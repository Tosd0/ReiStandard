`client_state` 不再被「来自未来」的时间戳锁死

条件写按 `updated_at` 判新旧，而这个值是客户端自己报上来的。设备时钟只要领先过真实时间（用户改过系统时间、时区或日期误操作），那一刻同步上去的行就带着一个还没到的时刻；之后这台设备每次上传都比它「旧」，写入被无声跳过。表现是某个 key 的同步一直失败、其它一切正常，而且删本地数据、重装应用都不管用——那一行在云端，客户端碰不到它，要等真实时间追上去才解得开。

现在服务端把自己的钟也带进判据：库里 `updated_at` 晚于服务端当前时刻的行按脏数据处理，写入和两条清理 DELETE 都对它放行。一次正常写入就把这一行的时间戳拉回现实，之后自愈。

正常路径一个字没变：库里那行的时间戳没跑到未来时，比它旧的写入照旧被跳过并出现在 `skippedEntries` 里，相同时间戳照旧覆盖。客户端报上来的时间戳不做改写——entry 上的 `version` 护栏允许是单调递增的版本号，把它钳到「不超过当前时刻」会压坏这种用法。
